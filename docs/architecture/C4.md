# CodeXPT architecture (C4)

**Status:** living document · **Version:** 0.2 draft · **Last reviewed:** 2026-10-10

## Scope and current status

The released `v0.1.0-local-mvp` remains a single-user local Rust process backed by SQLite. The current `main` candidate adds an experimental OIDC/session/workspace path and a digest-pinned Docker image. Local tests and container smoke checks pass, but there is no live identity provider or hosted service yet. The full HTTP authorization matrix, hosted callback, invitation delivery, hosted recovery, and end-to-end deployment checks remain open. Participant labels in local mode are declarations, not authenticated identities. Do not present this candidate as a public multiuser service.

## Runtime/deployment view (Level 4)

The local process runs on the user's workstation. CLI-only commands open SQLite without listening. `codexpt serve` binds `127.0.0.1:4173` when OIDC is not configured and serves embedded static assets plus the local API. The active hosted candidate places the Vite frontend and `/api/*` proxy on Vercel, with Rust/Axum and SQLite on Railway. Vercel owns `codexpt.jappi.net.pe`; Railway uses its generated HTTPS hostname. Vercel's function forwards API calls with a server-side proxy credential and no-store behavior; Rust validates the Railway transport Host, exact browser Origin and CSRF, and requires exactly one correct proxy credential. Only a generic liveness path is public; dependency readiness is behind the proxy. The digest-pinned container requires complete OIDC, host, origin, callback, proxy credential, and `/data` volume configuration, runs as UID 10001 with a read-only root filesystem. The topology is prepared locally, not deployed; identity, proxy semantics, authorization, Railway recovery, and hosted E2E gates remain open. Back up through SQLite's online backup API; do not copy only the main DB file while WAL writes are active.

## Quality attributes

- **Durability:** SQLite transactions and event records; backup/restore is an operator responsibility.
- **Consistency:** expected-state transition checks, uniqueness constraints, foreign keys, immediate transactions.
- **Auditability:** each successful state/message operation appends a sequenced event in the same transaction.
- **Privacy:** local data by default; never put secrets or confidential customer data into message bodies.
- **Identity:** participant names are claims, not verified principals, until authenticated adapters exist.
- **Recoverability:** process restart reopens persisted state; migrations and backup recovery require dedicated validation before release.
- **Browser boundary:** Host and Origin allowlists, JSON-only writes, a 32 KiB request limit, CSP, no-store, and loopback bind reduce cross-origin/browser risk. Any local process can still make requests; loopback does not authenticate a user.

## Trust boundaries

1. Human/agent-authored task and message text is untrusted input.
2. Actor labels are user-controlled and carry no authorization proof.
3. Evidence locators may point to arbitrary resources; v0.1 stores locators and declared hashes but does not fetch or verify them.
4. The local filesystem and OS account are trusted for this single-user prototype. This is not a multi-tenant service boundary.
5. Any future adapter must treat remote model output as untrusted and must not execute it or grant repository/infrastructure permissions by default.

## Hosted beta candidate (prepared, not deploy-ready)

The local MVP above remains the released architecture. The selected hosted candidate separates the Vercel public origin from the Railway transport origin while preserving a same-origin browser API:

```mermaid
flowchart LR
    Browser["Browser"] -->|HTTPS · codexpt.jappi.net.pe| Vercel["Vercel\nVite frontend + API proxy"]
    Vercel -->|HTTPS · generated Railway hostname\nproxy secret, no-store| Railway["Railway service\nRust/Axum API"]
    Browser -->|Authorization Code + PKCE| IdP["Configured OIDC identity provider"]
    IdP -->|registered callback · Vercel origin| Browser
    Railway --> AuthApp["Identity application service\ntrusted principal + policy"]
    AuthApp --> SQLx["SQLx identity adapter"]
    SQLx --> SQLite[("SQLite on persistent /data volume\nsingle service instance")]
    Railway --> Core["Protocol/domain core\nno HTTP or OIDC types"]
```

The application owns the OIDC callback and server-side session. The browser receives a host-only HttpOnly cookie under the Vercel domain and safe profile/role data, never provider tokens. Browser requests stay same-origin; the backend sees Vercel's exact Origin through the proxy, so credentialed CORS is not needed. Mutations still require Origin and CSRF validation. The Vercel domain is associated with the project, but the Railway project, generated hostname, compatible OIDC app, hosted recovery and end-to-end proxy have not been verified. Vercel Functions add usage-based cost; Hobby is limited to personal/non-commercial use and Pro currently lists at US$20/month, so this selection does not meet the earlier sub-US$1 target for a commercial deployment. AWS EC2 + SQLite + S3 remains a documented alternative with an estimated fixed baseline of approximately US$17.51/month. The Workers/D1 design remains an isolated spike; Rust/Axum/SQLx/SQLite stays authoritative until compatibility and safety gates pass. This repository has no registered OpenAI website OAuth client. Signing into an identity provider does not grant ChatGPT transcript access; local Codex and ChatGPT connectors are separate, user-authorized integrations. See [ADR-0013](../adr/0013-vercel-railway-split-hosting.md), [ADR-0006](../adr/0006-local-agent-runner-inbox.md), [ADR-0007](../adr/0007-workers-d1-hosting-spike.md), [ADR-0004](../adr/0004-identity-v1.md), [ADR-0005](../adr/0005-openai-chatgpt-auth-and-agent-connections.md), [the threat model](../identity-v1/THREAT-MODEL.md), and [the deployment plan](../deployment/PLAN.md).

The identity model distinguishes a verified human, a future agent runtime, a provider connection, a local OS-bound operator, and a system event. A provider connection is not an actor. Historical actor labels remain unverified declarations; migration does not infer that `human:cesar` is the verified user César. See the [identity contracts](../identity-v1/CONTRACTS.md) and [login design direction](../identity-v1/LOGIN-DESIGN.md).
